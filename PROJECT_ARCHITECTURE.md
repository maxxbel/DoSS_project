# Архитектура проекта — Система рецензирования документов (MVP)

## Краткое описание продукта

Серверная часть системы рецензирования документов. Автор создаёт заявку на рецензирование и прикрепляет документ. Рецензент берёт заявку в работу, проверяет документ, оставляет комментарий и либо отправляет на доработку, либо утверждает. Автор вносит исправления и загружает новую версию. Админ управляет учётными записями, может открепить/назначить рецензента и удалить заявку.

В MVP не входят: фронтенд, реальное хранилище файлов (S3 и аналоги), внешняя аутентификация (vk_id и аналоги). Хранилище файлов вынесено за границу продукта, поэтому MVP хранит только метаданные/ссылки на документы.

## Роли и полномочия

| Роль      | Доступно                                                                          | Недоступно                                                     |
|-----------|-----------------------------------------------------------------------------------|----------------------------------------------------------------|
| Автор     | Создавать заявки, загружать исправленные документы, просматривать свои заявки и комментарии | Просмотр чужих заявок, рецензирование, утверждение, функции админа |
| Рецензент | Забирать свободные заявки, оставлять комментарии, отправлять на доработку, утверждать документы | Просмотр заявок, не взятых в работу, создание заявок, функции админа |
| Админ     | Создавать учётные записи, откреплять/назначать рецензента, удалять заявку          | Создание заявок, рецензирование                                 |

Неавторизованные пользователи не имеют доступа.

## Модель данных

### Пользователь (User)
- Id (GUID)
- Имя/логин (уникально)
- Хэш пароля + соль (хранятся; вход через JWT)
- Роль: Author | Reviewer | Admin
- CreatedAt

### Заявка (ReviewRequest)
- Id (GUID)
- AuthorId (User)
- Заголовок / описание (текст)
- DocumentReference (ссылка/идентификатор файла во внешнем хранилище)
- Status: `Draft | Submitted | InWork | InRework | Approved`
- AssignedReviewerId (User, nullable — ставится при взятии в работу)
- CreatedAt, UpdatedAt

Жизненный цикл заявки:
- Создание автором → `Submitted`
- Рецензент берёт в работу → `InReview`
- Рецензент отправляет на доработку с комментарием → `InRework`
- Автор загружает новую версию → обратно в `InWork` (по описанию сценария — «в работе»)
- Рецензент утверждает → `Approved`

### Версия документа (DocumentVersion)
- Id (GUID)
- ReviewRequestId
- FileReference / метаданные (uri, имя файла, размер, media-type — плейсхолдер)
- UploadedBy (User)
- UploadedAt
- У заявки может быть несколько версий за цикл рецензирования.

### Комментарий (Comment)
- Id (GUID)
- ReviewRequestId
- AuthorId (кто написал комментарий — обычно рецензент)
- Text
- CreatedAt

## Уровень применения и контракты

В системе есть два уровня ответственности:

- доменная модель и бизнес-правила
- применение, то есть сценарии, которые используют модель

Уровень применения не хранит состояние и не знает про HTTP. Он принимает входные данные, проверяет условия и вызывает операции над моделью или репозиториями.

### Контракты доступа к данным

Основные сценарии:

- Регистрация и вход
  - создание учётной записи
  - проверка уникальности логина
  - хранение хэша и соли
  - выдача токена после проверки пароля
- Работа с заявками
  - создание заявки автором
  - просмотр своих заявок
  - получение доступных заявок рецензентом
  - получение назначенных заявок рецензентом
  - взятие заявки в работу
  - добавление комментария и отправка на доработку
  - загрузка новой версии
  - утверждение
- Административные действия
  - создание пользователя
  - назначение или открепление рецензента
  - удаление заявки

Каждый сценарий должен проверять:

- существование сущности
- принадлежность или роль текущего пользователя
- допустимость перехода состояния

## Аутентификация и авторизация

Используются токены доступа JWT.

Основные правила:

- Первая учётная запись может быть создана без предварительного токена (самый первый администратор).
- Дальнейшие регистрации требуют токен администратора.
- Вход возвращает токен.
- Защищённые эндпоинты требуют валидный токен.
- Доступ к операциям контролируется по роли и принадлежности ресурса.

## Поведение API

API представляет операции уровня применения через HTTP.

Основные группы эндпоинтов:

- auth
  - регистрация
  - вход
- requests
  - создание заявки
  - получение списка
  - получение по Id
  - переходы: взятие в работу, комментарий/доработка, версия, утверждение
- admin
  - создание пользователя
  - перекомплектовка рецензента
  - удаление заявки

Требования к API:

- чёткое разделение прав
- предсказуемые коды ответов
- единообразная обработка ошибок
- отсутствие доступа к «чужим» ресурсам для обычных ролей

## Ошибки и граничные случаи

Система должна корректно обрабатывать:

- отсутствие сущности
- попытку выполнить операцию от имени не того пользователя
- недопустимый переход статуса
- дублирование логина
- неверный пароль при входе
- отсутствие прав на административные действия

## Архитектура для S03


### Компоненты

- Клиент
  - сайт, мобильное приложение или HTTP-клиент
  - формирует запросы и показывает результаты
  - не является доверенной стороной с точки зрения сервера
- Сервер / API
  - принимает HTTP-запросы
  - проверяет аутентификацию и роли
  - передаёт действия в сервис предметной области
  - возвращает ответы и обрабатывает ошибки
- Сервис предметной области
  - реализует сценарии: создание заявки, взятие в работу, комментарии, доработка, версии, утверждение, администрирование
  - проверяет состояние и разрешение операции
  - не зависит от транспорта и способа хранения
- Хранилище состояния
  - хранит пользователей, заявки, версии, комментарии
  - является источником сохранённого состояния
  - меняется только через операции, прошедшие проверку
- Внешнее хранилище файлов
  - в MVP файлы не хранятся в серверной базе
  - сервер хранит только ссылку или метаданные
  - содержимое файла не входит в доверенное состояние сервера

### Потоки данных и места принятия решений

Важные потоки для анализа:

- автор создаёт заявку
  - клиент отправляет данные заявки
  - сервер проверяет аутентификацию и роль автора
  - сервис предметной области создаёт заявку и устанавливает начальный статус
  - хранилище фиксирует новое состояние
- рецензент берёт заявку в работу
  - клиент передаёт идентификатор заявки
  - сервер проверяет, что запрос отправляет авторизованный рецензент
  - сервис предметной области проверяет, доступна ли заявка, и назначает рецензента
  - статус меняется, результат сохраняется
- рецензент отправляет на доработку
  - клиент передаёт идентификатор заявки и комментарий
  - сервер проверяет доступ к заявке
  - сервис предметной области создаёт комментарий и меняет статус
  - хранилище фиксирует комментарий и новое состояние
- автор загружает новую версию
  - клиент передаёт метаданные или ссылку на файл
  - сервер проверяет, что запрос идёт от автора заявки
  - сервис предметной области добавляет версию и меняет статус
  - хранилище сохраняет новую версию
- администратор удаляет заявку
  - клиент передаёт идентификатор заявки
  - сервер проверяет права администратора
  - сервис предметной области удаляет заявку
  - хранилище фиксирует удаление

Для каждого потока важно показать:

- откуда входят данные
- какой компонент проверяет токен и роль
- какой компонент решает, разрешена ли операция
- какие данные меняются
- куда записывается результат

### Границы доверия

Граница доверия — это место, где система перестаёт предполагать, что входные данные или субъект автоматически корректны. За такой границей нужно проверять идентичность, разрешение и допустимость операции.

#### 1. Клиент ↔ Сервер

- стороны: клиент и сервер
- что передаётся: запросы, заголовки, токен, параметры, идентификаторы заявок и пользователей, текст, ссылки, статусы
- почему клиент недоверен: клиент может быть чем угодно, запрос может быть изменён или подан от имени другого пользователя, если сервер не проверил это сам
- что проверяет сервер:
  - валидность токена
  - соответствие пользователя и роли
  - возможность доступа к запрашиваемому ресурсу
  - допустимость операции с точки зрения состояния

Важно: отсутствие кнопки в интерфейсе, скрытое поле или проверка на клиенте не делают серверный запрос доверенным.

#### 2. Сервер ↔ Внешнее хранилище файлов

Если файлы хранятся не в серверной базе, а во внешней системе, возникает вторая содержательная граница.

- стороны: сервер и внешний сервис хранения
- что передаётся: ссылки, имена, метаданные, результаты обращения к файлу
- почему это граница: сервер не должен автоматически полагать, что файл соответствует созданной ссылке, что имя корректно, что внешняя сторона уже проверила доступ
- что проверяет сервер:
  - что хранится в метаданных и ссылке
  - что файл относится к конкретной заявке или версии
  - что доступ и смысл ссылки соответствуют тому, что сервер сам установил

Содержимое файла в такой схеме — не часть доверенного состояния сервера, а внешний объект, связанный с ним.

#### 3. Внутренняя граница: API ↔ Сервис предметной области

Это логическая граница внутри сервера.

- стороны: периферийный слой и слой предметной области
- что передаётся: запросы и параметры, уже выбранные на более внешнем уровне
- что проверяет сервис предметной области:
  - существует ли объект
  - принадлежит ли операция текущему пользователю
  - допустим ли переход состояния
  - не нарушает ли операция согласованность модели

Это важно, потому что даже если API уже проверило токен и роль, сценарий всё равно должен подтвердить, что операция значима и корректна в текущем состоянии.

## Недоверенный ввод

В модели угроз полезно явно перечислить, что нельзя принимать на веру.

Обычно недоверенным является:

- идентификаторы в запросе
- статусы, переданные извне
- текстовые данные, ссылки, имена, типы
- роль, если она получена не из проверенного токена
- любые параметры, которые клиент добавляет или меняет
- данные, связанные с файлами, если они не были сгенерированы или проверены сервером

Такие данные не являются «вредоносными» по умолчанию, но они не могут быть основанием для принятия решений без проверки.

## Что находится внутри доверенной части

Внутри доверенной части находятся те элементы, которые играют роль арбитра и хранят состояние по правилам системы.

Обычно это:

- логика предметной области, которая сама решает, разрешена ли операция
- хранилище, в которое записывается результат после проверки
- внутренние правила переходов и связей между объектами

Здесь предполагается не то, что клиент прислал правильный id, а то, что система решила, что операция допустима.

## Ссылки на угрозы

Эта архитектура и границы доверия — вход для модели угроз. На их основе формируются T-*, каждая со связью к SR и к конкретному потоку или точке входа.

Примеры направлений для угроз:

- подмена идентификатора заявки при попытке изменить чужую заявку
- некорректный переход статуса, если проверка состояния неполная
- несанкционированное просмотр или изменение ресурсов, если проверка принадлежности слабая
- проблемы с доверием к внешнему хранилищу файлов, если сервер полагается на ссылку без проверки

Это не каталог атак, а структура, по которой дальше строятся угрозы и приоритеты.
